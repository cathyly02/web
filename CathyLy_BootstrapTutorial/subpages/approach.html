Four things that stay true across projects

Open each one for how it plays out in practice.

Start with the mechanic that's fun before deciding what it teaches. A game that's a chore with a learning objective bolted on rarely gets played twice — the fun has to come first, then the learning gets built into it.

Clinicians, teachers, and kids get pulled in early — not to approve a finished thing, but to shape what gets built in the first place. That's where the real constraints show up.

Paper prototypes and quick playtests catch the bad ideas cheaply. Code comes after the mechanic has already survived a few rounds of "does this even make sense."

Whether it's a neurodivergent player, a maker-space kid with limited fine motor control, or a family working within a tight budget, access constraints get treated as design input from day one, not a retrofit at the end.
